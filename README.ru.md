Загрузка
========

Каждый выпуск AMORPH на
[странице выпусков](https://github.com/ij3tt/amorph/releases) содержит
готовые к запуску версию для командной строки и графический интерфейс
(см. ниже «Графический интерфейс») для трёх систем:

| файл | система |
|---|---|
| `AMORPH-<tag>-windows-x64.zip` | Windows 10 и новее, 64-битная (x86-64) |
| `AMORPH-<tag>-linux-x64.tar.gz` | Linux на x86-64 с glibc 2.34 и libstdc++ из GCC 13 или новее: Ubuntu 24.04, Debian 13, Fedora 39 и новее |
| `AMORPH-<tag>-macos-arm64.zip` | macOS 11 и новее на Apple Silicon (M1 и новее) |
| `AMORPH-GUI-<tag>-windows-x64.zip` | графический интерфейс, Windows 10 и новее, 64-битная |
| `AMORPH-GUI-<tag>-linux-x64.tar.gz` | графический интерфейс, Linux на x86-64 (собран на Ubuntu 24.04, как и версия для командной строки) |
| `AMORPH-GUI-<tag>-macos-arm64.zip` | графический интерфейс, macOS на Apple Silicon |
| `AMORPH-<tag>-SHA256SUMS.txt` | контрольные суммы SHA-256 шести архивов |

`<tag>` — версия, например `v1.0.0`; что изменилось в каждой, описано в
[CHANGELOG.md](CHANGELOG.md). Каждый архив содержит одну папку,
`AMORPH-<tag>-<система>`, в которой

* `AMORPH` (`AMORPH.exe` в Windows) — сэмплер;
* Python-постобработка: `showresults.py` и модули, которые он использует:
  `display.py`, `dnest_functions.py`, `amorph_stats.py`,
  `amorph_results.py` и `amorph_archive.py`;
* `config.yaml` — настройки прогона, настроенные на `easy_data.txt`;
* `OPTIONS` и `OPTIONS_AGGRESSIVE` — настройки сэмплера DNest4;
* `easy_data.txt` — пример набора данных (остальные лежат в `src/`
  репозитория);
* `README.md` и `README.ru.md` (этот файл), `LICENSE` (GNU GPL версии 3)
  и, в `licenses/`, лицензии библиотек, встроенных в исполняемый файл:
  DNest4, yaml-cpp и, в Windows, среды выполнения mingw-w64.

Архив графического интерфейса содержит одну папку, `AMORPH-GUI`, с
программой и всем, что ей нужно, включая сэмплер: устанавливать Python и
его пакеты не нужно. Распакуйте его куда угодно и запустите в этой папке
`AMORPH-GUI.exe` (Windows), `AMORPH-GUI.app` (macOS) или `./AMORPH-GUI`
(Linux). В распакованном виде он занимает около 100–200 МБ. В папке также
лежат README, `LICENSE` и, в `licenses/`, лицензии того, что входит в
программу (Qt for Python — под GNU LGPL; его библиотеки — отдельные файлы
программы).

Архив для командной строки распакуйте куда угодно и запускайте AMORPH в
этой папке: он читает `config.yaml` из папки, в которой запущен (см. ниже
«Руководство по установке и работе»). В Linux и macOS это `./AMORPH` в терминале; в
Windows можно и дважды щёлкнуть по `AMORPH.exe`. Исходный код выпуска тоже
есть на его странице. Исполняемые файлы, которые CI собирает при каждом
изменении, — артефакты запусков GitHub Actions, и через несколько недель
они удаляются; выпуски остаются.

Проверить загруженный файл по контрольным суммам: в Linux
`sha256sum -c --ignore-missing AMORPH-<tag>-SHA256SUMS.txt`; в macOS
`shasum -a 256 AMORPH-<tag>-macos-arm64.zip`, а в Windows
`Get-FileHash AMORPH-<tag>-windows-x64.zip` в PowerShell — и сравнить со
своей строкой файла.

### Исполняемые файлы не подписаны

Windows и macOS предупреждают, прежде чем запустить загруженную программу,
не подписанную известным разработчиком, а исполняемые файлы AMORPH не
подписаны.

**Windows (SmartScreen).** При первом запуске `AMORPH.exe` двойным щелчком
Windows может показать «Система Windows защитила ваш компьютер». Нажмите
«Подробнее», затем «Выполнить в любом случае». Или, до распаковки
zip-файла: правый щелчок по нему → Свойства → отметьте «Разблокировать» →
OK; тогда распакованные файлы не помечены как загруженные.

**macOS (Gatekeeper).** В первый раз macOS отказывается открыть `AMORPH`
(«не удаётся открыть, так как не удалось проверить разработчика» или
«Apple не может проверить...»). Разрешите его один раз:

* macOS 14 и старше: в Finder правый щелчок (или щелчок с Control) по
  `AMORPH` → Открыть, и ещё раз «Открыть» в диалоге;
* macOS 15 и новее: попробуйте открыть его один раз, затем Системные
  настройки → Конфиденциальность и безопасность, и «Все равно открыть»
  рядом с сообщением об `AMORPH`;
* или в Терминале, в папке AMORPH, снимите пометку загрузки:
  `xattr -d com.apple.quarantine AMORPH`.

Открытый из Finder, AMORPH запускается в окне Терминала в вашей домашней
папке и сразу останавливается, так как не находит там `config.yaml`; так и
должно быть. Дальше запускайте его из его папки в Терминале: `cd` в папку,
затем `./AMORPH`. Python-скриптам ничего этого не нужно.

Графический интерфейс разрешается так же, один раз: `AMORPH-GUI.exe` в
Windows и `AMORPH-GUI.app` в macOS, или в Терминале в его папке
`xattr -dr com.apple.quarantine AMORPH-GUI.app` (`-r`: приложение — это
папка с файлами). Он запускает сэмплер, упакованный внутри, которому тогда
больше ничего не нужно.

Руководство по установке и работе:
==================================

AMORPH размещён по адресу:

[https://bitbucket.org/eggplantbren/amorph]([https://bitbucket.org/eggplantbren/amorph)

Репозиторий включает исходный код, Python-скрипты для просмотра
результатов и примеры наборов данных, большей частью в подкаталоге `src`.
Самый простой способ использования AMORPH — выпуск с исполняемым файлом
для вашей системы (см. выше «Загрузка»).
Python-скрипты используют пакеты Numpy, matplotlib, Pandas и yaml и
тестировались только с Python 3. Удобный дистрибутив Python с
предустановленными пакетами — [Anaconda](https://www.anaconda.com/download/).

Программу AMORPH можно установить в любое место на компьютере. Все файлы
данных для анализа должны быть в формате .txt, с разделением пробелами,
без заголовков (то есть просто два столбца чисел). Для простоты текстовые
файлы для обработки следует помещать в ту же папку, что и программу AMORPH.
Чтобы настроить запуск, отредактируйте файл `config.yaml`, указав все
детали файла данных и другие параметры, которые вы хотите изменить.

В репозитории хранятся четыре тестовых набора данных
(`0%glass_rhyolite_Emperyon.txt`, `50% glass .02step3secdwell.txt`,
`90%_glass_basalt_Emperyon.txt` и `easy_data.txt`) и ещё два образца,
`G30RAW_amorph.txt` и `N3RAW_amorph.txt` (26–46°), демонстрирующих
неоднозначность, описанную ниже в разделе «Форма кристаллических пиков».
Полные сканы этих двух образцов (Cu Kα, 5–70°, шаг 0.02°) — `G30RAW.txt`
и `N3RAW.txt`, а `*_20-50.txt` и `*_15-70.txt` — их части.
Программа работает до тех пор, пока не будет сгенерировано 10 000
сохранённых наборов параметров. Результаты можно просматривать в любой
момент, однако закрытие программы до достижения 10 000 снизит точность
итоговых расчётов. После некоторого времени работы результаты можно
посмотреть, запустив Python-скрипт `showresults.py`:

```
python showresults.py
```

Он печатает отчёт о прогоне: log(Z), информацию и эффективный размер
выборки сэмплера, долю аморфной фазы и форму широкой компоненты (среднее
± стандартное отклонение по апостериорным выборкам) и диагностику
апостериорного распределения (см. ниже «Диагностика апостериорного
распределения»). Он записывает `macroquantities.csv`, по строке на
апостериорную выборку, и архив прогона (ниже), а затем показывает рисунки
один за другим: уровни сэмплера, сжатие и долю принятых шагов по уровням,
правдоподобие и апостериорные веса в зависимости от log(X), модель с её
частями и данными, остатки и гистограммы числа узких пиков, доли аморфной
фазы, а также центра, полуширины, асимметрии и негауссовости широкой
компоненты.

### Архивы прогонов

Следующий прогон перезаписывает выходные файлы, а они занимают сотни
мегабайт и больше. Поэтому `showresults.py` также сохраняет результаты в
один сжатый файл в папке прогона с именем по файлу данных и времени
последнего сохранения, например `easy_data_2026-10-25_1530.amorph`. Это
zip-файл в несколько мегабайт, в нём

* `report.html`: отчёт и все рисунки, для браузера;
* `report.txt` и `summary.json`: отчёт текстом и его числа для программ;
* `input/`: `config.yaml`, параметры DNest4 и файл данных, и `dnest4/`:
  `levels.txt`, `sample_info.txt` и `weights.txt`;
* `particles.csv`: по строке на сохранённую выборку — её параметры, log
  правдоподобия, апостериорный вес, доля аморфной фазы и форма широкой
  компоненты; `posterior.csv`: то же для апостериорных выборок;
* `peaks.npz`: положение, log амплитуды и ширина каждого пика каждой
  сохранённой выборки;
* `curves.npz`: апостериорное среднее, квантили 5, 16, 50, 84 и 95% и 50
  апостериорных выборок фона, широкой и узкой компонент и модели.

`README.txt` в архиве описывает каждый файл. Записать архив папки
прогона, напечатать отчёт архива или записать его рисунки:

```
python amorph_archive.py RUN_FOLDER [--out FILE.amorph]
python amorph_archive.py --show FILE.amorph
python amorph_archive.py --figures FOLDER FILE.amorph
```

В Python `amorph_archive.read("FILE.amorph")` возвращает результаты
прогона, а `amorph_results.FIGURES` рисует каждый их рисунок на рисунке
matplotlib.

Графический интерфейс
=====================

`src/amorph_gui` — настольная программа для всего описанного выше: она
открывает файл данных, настраивает и запускает сэмплер с одним или
несколькими seed, показывает и сравнивает результаты. Её интерфейс на
русском языке (весь текст собран в `src/amorph_gui/strings.py`, чтобы его
можно было перевести).

Каждый выпуск содержит её собранной для Windows, Linux и macOS, с
сэмплером внутри, готовой к запуску (см. «Загрузка»). CI собирает её
PyInstaller'ом (`packaging/amorph_gui.spec`, `scripts/ci/gui_package.sh`)
на каждой системе и там же прогоняет самопроверку собранной программы;
сборки каждого изменения — артефакты запусков Build.

Из исходного кода ей кроме пакетов постобработки нужны PySide6 и
pyqtgraph, а также исполняемый файл AMORPH (см. «Использование исходного
кода»):

```
pip install PySide6 pyqtgraph
cd src
python -m amorph_gui [FILE]
```

`FILE`, если задан, — файл данных или архив прогона, который нужно
открыть. Программа запускает AMORPH, лежащий рядом с ней (в `src/`, в
`build/` CMake-сборки репозитория или внутри собранной программы) или в
PATH, если в «Настройки…» (или `--amorph PATH`) не указан другой.

В ней четыре экрана, перечисленных слева:

* «Данные и модель»: файл данных, прочитанный по правилам сэмплера
  (ошибка называет файл и строку), на графике, на котором перетаскиваются
  диапазон анализа и две контрольные точки фона. Полоса показывает, где
  могут быть широкие пики (`left_edge` и `right_edge` — доли диапазона
  анализа). В форме — все настройки `config.yaml` с ограничениями, которые
  проверяет AMORPH, файл параметров DNest4 (`OPTIONS_AGGRESSIVE` или
  `OPTIONS`) с наибольшим числом сохранений и число seed; по умолчанию
  `narrow_peak_nu: [1.0, 100.0]`. Перед прогоном программа проверяет, что
  контрольные точки лежат в диапазоне анализа, предупреждает, если данные
  не выходят за них с какой-либо стороны или нижняя граница ν меньше 1
  (см. «Рекомендуемые настройки и калибровка»), и ничего не запускает,
  пока есть ошибка. «Загрузить config.yaml…» и «Сохранить config.yaml…»
  читают и записывают настройки.
* «Прогоны»: каждый seed получает папку `runs/<дата>_<данные>_seed<k>/`
  (в папке из «Настройки…», по умолчанию `runs/` в текущей) с
  `config.yaml`, файлом параметров и точками диапазона анализа: у AMORPH
  нет настройки диапазона, поэтому программа записывает их туда. Seed
  (seed, seed + 1, …) идут один за другим. Экран показывает число
  сохранений и уровней и время, вывод сэмплера (он же сохраняется в папке
  как `run.log`) и модельную кривую последней сохранённой выборки.
  «Остановить» останавливает сэмплер, оставляет его полные сохранения,
  обрабатывает их и помечает прогон как неполный; ожидающие seed
  отменяются.
* «Результаты»: каждый прогон обрабатывается так же, как это делает
  `showresults.py`, и его архив записывается в его папку. Вкладки:
  «Итог» — медиана доли аморфной фазы с 50% и 90% интервалами, карточки
  диагностики (красная, если у доли ниже 0.2 больше 5% апостериорного
  веса; жёлтая, если больше 5% веса у предела числа узких пиков, если
  контрольные точки лежат вне данных или если прогон остановился раньше
  запланированного числа сохранений) и эффективный размер выборки;
  «Модель», «Распределения» и «Сэмплер» — рисунки `showresults.py` (на
  последней — log(Z), информация и эффективный размер выборки); «Полный
  отчёт» — отчёт. Каждый рисунок сохраняется в PNG, архив и апостериорные
  выборки (CSV) тоже.
* «Сравнение»: таблица архивов прогонов, например seed одной серии
  (добавляются, когда серия закончилась) или файлов `run.amorph`, которые
  выкладывают workflow experiment и validate. Для каждого архива: файл
  данных, настройки, seed, медиана доли с 50% интервалом, ещё и в виде
  полосы на общей для всех строк шкале, и апостериорный вес ниже 0.2 и у
  предела. Таблица выгружается в CSV и Markdown.

«Открыть архив…» на каждом экране показывает архив на «Результатах».
Как сказано на «Итоге», доля — это отношение интегральных
интенсивностей, а не массовая доля, а разброс между seed — ошибка
сэмплера от прогона к прогону, а не апостериорный интервал (см.
«Рекомендуемые настройки и калибровка»). Числа и рисунки — те же, что
дают `amorph_stats.py`, `amorph_results.py` и `amorph_archive.py`.

Проверки входных файлов
========================

Перед стартом сэмплера AMORPH проверяет `config.yaml` и файл данных.
Если что-то не так, программа останавливается с кодом выхода 1 и
сообщением, указывающим файл, строку и параметр:

* `config.yaml` должен быть корректным YAML и содержать все настройки из
  штатного файла. `num_threads`, `max_num_narrow_peaks` и
  `max_num_wide_peaks` — целые числа не менее 1, `control_points` — список
  из двух чисел по возрастанию, и `0 <= left_edge < right_edge <= 1`.
  Файлы, указанные в `data_file` и `dnest4_options_file`, должны
  существовать (относительные пути отсчитываются от папки, из которой
  запущен AMORPH).
* В файле данных на каждой строке два числа, x и y, разделённые
  пробелами, табуляцией или запятой. Пустые строки и строки, начинающиеся
  с `#`, пропускаются в любом месте файла. Должно быть не менее 10 точек
  данных, и x должен строго возрастать.

Например:

```
AMORPH: error: config.yaml: missing key 'inference_assumptions.control_points'
AMORPH: error: config.yaml, line 5: 'num_threads' must be at least 1, got '0'
AMORPH: error: config.yaml, line 8: cannot open the file 'my_data.txt' given by 'data_file' (relative paths start from the folder AMORPH runs in)
AMORPH: error: my_data.txt, line 12: expected two numbers (x and y), got '10.22 abc'
AMORPH: error: my_data.txt, line 40: the x values must be strictly increasing, but x = 10.76 follows x = 10.78 (line 39)
```

Когда `AMORPH.exe` запущен двойным щелчком, его окно остаётся открытым до
нажатия Enter, чтобы сообщение можно было прочитать. В командной строке,
терминале или скрипте программа завершается сразу.

Контрольные точки за пределами диапазона данных допускаются, с
предупреждением:

```
# WARNING: the background control points (5, 40) lie outside the range of the data (10 to 40). Check control_points in config.yaml.
```

Рекомендации по использованию
=============================

Основываясь на экспериментах, можно дать несколько рекомендаций по
оптимизации времени анализа и точности. Во-первых, время анализа зависит
от числа обрабатываемых точек данных. Поэтому для оптимизации времени мы
рекомендуем шаг по углу дифрактометра 0.02 градуса/шаг. Более крупные шаги
сократят время анализа, но связанное с ними уширение пиков может снизить
точность подгонки. Мы также рекомендуем сократить полный диапазон сканирования
до 10–40 градусов (2тета). Это даёт два преимущества: 1) уменьшается число
обрабатываемых точек и 2) вне этого диапазона дифрактограмма доминируется
только кристаллическими компонентами, поэтому включение больших значений
2тета смещает измеренные результаты в сторону более высоких измеренных
кристалличностей.

Положение фона. В статье используются линейные участки между 10–40° 2тета
для источников CuKα: фон — прямая под аморфным гало, а вне его он может
изгибаться. Поэтому контрольные точки ставят туда, где гало кончается, и
их выбор может заметно менять результат: см. «Рекомендуемые настройки и
калибровка». Для некоторых анализов,
обычно при большем числе точек (5–50 градусов 2тета) или для сильно
кристаллических материалов, численные настройки сэмплера DNest4 не
оптимальны для получения полезных результатов и их нужно сделать более
консервативными (что замедляет работу). Это обычно проявляется в выводе
Python как бледные цвета кривых модели на графиках (почти нет выборок из
апостериорного распределения) и малое число точек для последующих
гистограмм. Настройки можно изменить, открыв файл OPTIONS в любом
текстовом редакторе. Значения параметров на строке 4 (new level interval)
и строке 8 (Backtracking scale length) можно независимо удвоить. Заметим,
что хотя это улучшит выходные данные модели, оно значительно удлинит
время анализа. Поэтому мы рекомендуем менять только один из этих двух
параметров за раз.

Форма кристаллических пиков
============================

Узкие (кристаллические) пики — профили Стьюдента с общим для всех
параметром формы ν. Его априорное распределение логарифмически
равномерно между двумя значениями `narrow_peak_nu` в `config.yaml`, по
умолчанию `[0.1, 100.0]`, как в статье (максимально допустимый диапазон).
Профиль Стьюдента — это профиль Пирсона VII с показателем m = (ν + 1)/2:
ν = 1 — лоренцевский, большое ν приближается к гауссову, а ν < 1 даёт
хвосты тяжелее лоренцева.

Вблизи ν = 0.1 «узкий» пик помещает большую часть своей площади в широкие
хвосты, и несколько сотен таких пиков могут заменить аморфный горб. Для
некоторых образцов данные не могут различить эти два описания, и
апостериорное распределение доли аморфной фазы тогда имеет вторую моду у
нуля или около него. В запуске на `src/N3RAW_amorph.txt` (не более 500
узких и 100 широких пиков, ν в [0.1, 100]) около 12% апостериорного веса
имело долю ниже 0.2, с сотнями узких пиков при ν около 0.14–0.19 и
подгонкой не хуже основной моды. В том же запуске на
`src/G30RAW_amorph.txt` эта мода не имела веса.

Более узкий диапазон, например `narrow_peak_nu: [1.0, 100.0]` (нет
профилей с хвостами тяжелее лоренцева), меняет модель статьи:
сообщайте его вместе с результатами. В экспериментах, описанных в разделе
«Рекомендуемые настройки и калибровка», этот диапазон убирал низкую моду
в каждом запуске на N3RAW и G30RAW. `.github/workflows/experiment.yml`
сравнивает такие
настройки на этих двух образцах.

`config.yaml` может также задавать `seed` — целое число от 0 до
4294967295 для генератора случайных чисел сэмплера; без него
используется время.


Рекомендуемые настройки и калибровка
=====================================

Эксперименты на входящих в комплект образцах (pull request'ы #5, #6, #7 и
#10 и более поздние запуски, все — `.github/workflows/experiment.yml`)
обосновывают одну настройку, отличающуюся от статьи, показывают, насколько
важны контрольные точки фона и диапазон 2θ, и дают первую оценку точности
на трёх стандартах.
Каждый материал — один набор данных, прогнанный с несколькими сидами:
читайте числа ниже как наблюдавшиеся на этих образцах, а не как общую
точность метода.

* `narrow_peak_nu: [1.0, 100.0]`. При ν < 1 апостериорное распределение
  доли может иметь вторую моду у нуля или около него (см. «Форма
  кристаллических пиков»); при ν ≥ 1 эта мода не имела веса ни в одном из
  запусков на N3RAW и G30RAW. Это изменение модели статьи: сообщайте его
  вместе с результатами.
* `control_points`: снимайте и анализируйте диапазон 2θ, который с обеих
  сторон заметно выходит за аморфное гало, и держите фон прямым под всем
  гало, с контрольными точками там, где гало кончается.
  - Когда данные заметно выходят за гало, этого достигают края данных. На
    стандарте с 90% стекла (5–50°) контрольные точки на краях, `[5, 50]`,
    дали 0.83–0.84 против 0.79–0.80 с `[10, 40]`. На стандартах с 0% и 50%
    разница между двумя вариантами не превышала разброса между сидами,
    кроме одного коллапсировавшего запуска с `[10, 40]` на стандарте с 0%
    (0.33). На N3RAW и G30RAW, обрезанных до 20–50° (гало около 29–40°),
    фон, прямой от края до края, `[20, 50]`, имел log(Z) примерно на 10 нат
    выше, чем контрольные точки `[25, 45]`, на обоих образцах — больше, чем
    2–3 ната между сидами: данные предпочитают его. log(Z) сравнивает
    варианты только на одном и том же файле данных.
  - Без данных за гало фон ничем не закреплён, и результат зависит от
    выбора. На `N3RAW_amorph.txt` (26–46°, центр гало около 35°) доля была
    0.72 с `[10, 40]` и 0.63 с `[26, 46]`. Это решил полный скан
    (`N3RAW.txt`, 5–70°): когда фон закреплён данными с обеих сторон, доля
    в 26–46° во всех запусках была 0.56–0.68, ни разу не 0.72, а в десяти
    запусках с прямым фоном на 20–50° — 0.65–0.68. Значение 0.72 давала
    контрольная точка 10° вне данных, где фон экстраполировался; о такой
    точке AMORPH предупреждает. G30RAW дал в 26–46° 0.71–0.73 на 20–50°
    при обоих выборах контрольных точек, как и на одном 26–46°, и 0.72–0.77
    на 15–70°.
  - Даже с данными за гало выбор остаётся. На N3RAW, обрезанном до 20–50°,
    разумные варианты (контрольные точки на краях или в 25° и 45°) разносят
    долю в 26–46° по 0.63–0.68 — больше, чем разброс между сидами
    (0.01–0.02). Берите вариант с большим log(Z), а разброс по остальным
    приводите как неопределённость результата: для N3RAW в 26–46° около
    0.66 и 0.63–0.68 по разумным вариантам.
  - Более широкий диапазон не лучше. На 15–70° (с `left_edge: 0.2`,
    `right_edge: 0.95`, см. ниже, и лимитами 1000/200) четыре сида по
    10000 сохранений дали доли с разбросом 0.05–0.1 между сидами против
    примерно 0.01 на 20–50°: для N3RAW 0.63–0.68 по 15–70° и 0.56–0.66 в
    26–46°, для G30RAW 0.72–0.78 и 0.72–0.77. У апостериорного
    распределения несколько мод, и сиды оседают в разных. Запуск N3RAW с
    0.56 имел log(Z) −9581, на 15–20 нат ниже остальных (от −9561 до
    −9566): запуск, у которого log(Z) заметно ниже, чем у других сидов на
    тех же данных, упустил большую часть апостериорного распределения, и
    его отбрасывают или запускают заново. Обрабатывайте диапазон, который
    лишь немного выходит за гало, как 20–50° здесь; на более широком
    запускайте четыре сида или больше и приводите их разброс.
* Доля зависит от диапазона 2θ, по которому её считают: приводите диапазон
  вместе с ней. Проверьте, что `left_edge` и `right_edge` позволяют широким
  пикам лежать под каждым аморфным горбом диапазона. По умолчанию они
  покрывают 0.3–0.7 диапазона: на 15–70° это 31.5–53.5°, и второй горб
  N3RAW и G30RAW около 60° туда не попадает. С `left_edge: 0.2` и
  `right_edge: 0.95` (26–67°) широкая компонента взяла оба горба, и доля по
  15–70° была 0.63–0.68 для N3RAW и 0.72–0.78 для G30RAW против 0.63–0.66
  и 0.69 по 20–50°.
* Сравнение образцов, снятых и обработанных одинаково, надёжнее любой
  отдельной доли: G30RAW оказался аморфнее N3RAW на 0.04–0.08 на 20–50°
  при обоих выборах контрольных точек и в среднем на 0.10 по 15–70°, где
  отдельные запуски разбросаны сильнее.
* `max_num_narrow_peaks: 500` и `max_num_wide_peaks: 100`. На стандартах
  удвоение лимитов не сдвинуло измеренную долю, но удлинило запуски до
  двух раз. Поднимайте их до 1000/200, если диагностика (ниже) показывает
  большой апостериорный вес у лимита (скажем, выше 20%).

Большая часть этих запусков сделана до ускоренного сэмплера из pull
request'а #14, у которого та же модель. По четыре сида по 10000
сохранений до и после него дали одинаковые результаты в пределах разброса
между сидами: на N3RAW по 20–50° доля 0.640–0.645 до и 0.632–0.641 после
(в среднем 0.659 и 0.656 в 26–46°), на стандарте с 50% — 0.498–0.507 и
0.496–0.512, тогда как неопределённость каждого запуска была ±0.02–0.04;
log(Z) различался меньше, чем его разброс между сидами (0.5 ната на
N3RAW, 3 на стандарте с 50%). Ускоренный сэмплер делал в 2.4–3.2 раза
больше сохранений в минуту.

Стандарты
---------

Три входящих в комплект образца имеют известное содержание стекла:
стандарты с 0% (риолит) и 90% (базальт), снятые в 5–50°, и стандарт с 50%,
снятый в 10–40° с другим шагом. При ν ≥ 1 и контрольных точках на краях
данных (pull request #7: по четыре сида с каждым из двух лимитов) медианы
запусков были такими:

| истинная доля | измеренная | замечания |
| --- | --- | --- |
| 0% | 0.00 – 0.05 | несколько апостериорных распределений коллапсировали в одно значение; до 72% веса у лимита в 500 узких пиков; 3 из 4 запусков с лимитом 1000 остановлены по лимиту времени |
| 50% | 0.50 – 0.53 | |
| 90% | 0.82 – 0.85 | 3 из 4 запусков с лимитом 1000 остановлены по лимиту времени |

Что это показывает и чего не показывает:

* AMORPH измеряет отношение интегральных интенсивностей двух компонент
  (`src/amorph_stats.py`), а не массовую долю стекла. Связь между ними
  зависит от материала и прибора; в статье для этого строится
  калибровочная кривая. Чтобы перевести измеренную долю в содержание
  стекла, нужны стандарты того же типа материала, снятые на том же приборе
  в том же диапазоне 2θ.
* Эти три стандарта — разные материалы, снятые в разных диапазонах, и часть
  их запусков не сошлась по критериям ниже. Они показывают величину
  эффекта на краях шкалы — около +3 пунктов при 0% и около −7 пунктов при
  90%, — но калибровочной кривой не являются: не исправляйте по ним доли
  других образцов. В частности, N3RAW и G30RAW — другие материалы, снятые
  в 5–70°.
* Разброс между сидами, около ±1–2 пунктов при 50% и 90%, — это разброс
  сэмплера от запуска к запуску на одном файле данных. Это не точность
  метода и не воспроизводимость измерения: для неё нужны повторные
  измерения образца.

Диагностика и представление результатов
---------------------------------------

Всегда запускайте `scripts/diagnose_posterior.py` (см. «Диагностика
апостериорного распределения»), прежде чем называть долю:

* Большой вес у лимита узких пиков (выше ~20%) означает, что их число
  задаёт предел априорного распределения, а не данные: перезапустите с
  удвоенными лимитами.
* Коллапсированное апостериорное распределение (крошечный интервал
  [q25, q75]) или малое эффективное число выборок означает, что запуск не
  сошёлся: перезапустите с другим `seed`.
* Вблизи 0% или 100% сэмплер иногда «втыкается» ровно в 0 или 1; доли
  ниже ~0.05 читайте как «примерно ноль», а для долей выше ~0.9
  перезапустите со вторым сидом.
* Запуск, остановленный по лимиту времени раньше запланированного числа
  сохранений, — предварительный.

Важные образцы запускайте хотя бы с двумя сидами и приводите разброс
между ними отдельно от апостериорного интервала: интервал — это
неопределённость при данных, а разброс — ошибка сэмплера от запуска к
запуску. Приводите вместе с долей диапазон 2θ и контрольные точки, а если
их выбор сдвигает долю сильнее, чем сиды, — и этот разброс.


Использование исходного кода
============================
Если вы не хотите использовать `AMORPH.exe` и предпочитаете скомпилировать
AMORPH самостоятельно, вам понадобятся компилятор C++14 и CMake 3.16+.

Обе зависимости включены в репозиторий (vendored), так что ничего
устанавливать отдельно не нужно, а сборке не требуется доступ к сети:
DNest4 в `external/DNest4` и yaml-cpp в `external/yaml-cpp` (обе под
лицензией MIT, см. их файлы `LICENSE`).

### Linux / macOS

```bash
cmake -B build -S . -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./build/AMORPH
```

### Windows (кросс-компиляция из Linux)

```bash
sudo apt-get install g++-mingw-w64-x86-64
cmake -B build-win -S . -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_SYSTEM_NAME=Windows \
      -DCMAKE_CXX_COMPILER=x86_64-w64-mingw32-g++
cmake --build build-win -j
```

Полученный `build-win/AMORPH.exe` статически слинкован и не требует
дополнительных DLL. Работает и нативная сборка под Windows (MSYS2 /
MinGW-w64) — просто уберите `-DCMAKE_SYSTEM_NAME=Windows` и указания
компилятора.

### Дымовой тест (smoke test)

`scripts/smoke_test.sh` запускает сэмплер на входящем в комплект примере
с намеренно крошечной конфигурацией и проверяет, что создаются ожидаемые
выходные файлы:

```bash
bash scripts/smoke_test.sh build/AMORPH build/smoke
```

Он также проверяет, что `config.yaml`, ссылающийся на отсутствующий файл
данных, заставляет AMORPH сразу завершиться с кодом 1 и сообщением об
ошибке (на Windows — без ожидания Enter), и что первая строка вывода —
`# AMORPH` и версия из `CMakeLists.txt`.

### Модульные тесты

`tests/test_model.cpp` проверяет правдоподобие, фон и формы пиков, а
`tests/test_input.cpp` — проверки файла данных и `config.yaml`. Оба
собираются вместе с AMORPH и запускаются через ctest:

```bash
(cd build && ctest --output-on-failure)
```

### Тесты Python-постобработки

`tests/test_postprocess.py` проверяет `amorph_stats.py`, `display.py` и
`export_pgf.py` на синтетическом запуске, созданном
`scripts/make_demo_posterior.py` (нужны numpy, matplotlib, pandas, pyyaml
и pytest):

```bash
python -m pytest tests
```

### Тесты графического интерфейса

`tests/gui/` проверяет интерфейс без экрана: форма записывает и читает
`config.yaml` без изменений, проверки перед прогоном, архив поддельного
прогона из `tests/test_results.py` на «Результатах», таблицу сравнения, а
также прогоны, остановку и сбои поддельного сэмплера. Нужны PySide6,
pyqtgraph и pytest-qt; без них тесты пропускаются:

```bash
QT_QPA_PLATFORM=offscreen python -m pytest tests/gui
```

Самопроверка прогоняет `easy_data.txt` из комплекта с крошечными
параметрами DNest4 дымового теста через сам интерфейс: два seed до конца
и третий, который она останавливает, их обработку и архивы, сравнение и
повторное открытие архива. Она сохраняет снимок каждого экрана в
указанную папку, а прогоны — в `runs/` в ней:

```bash
cd src
QT_QPA_PLATFORM=offscreen python -m amorph_gui --self-test ../build/gui-self-test --amorph ../build/AMORPH
```

### Непрерывная интеграция

Репозиторий собирается на двух CI-сервисах, которые запускают одни и те
же скрипты из `scripts/ci/`:

* GitHub Actions (`.github/workflows/build.yml`), при пуше в master и в
  pull request'ах: собирает Linux-исполняемый файл и прогоняет тесты и
  дымовой тест на нём, кросс-компилирует `AMORPH.exe` с mingw-w64 и
  прогоняет дымовой тест на нём на Windows-раннере, а также собирает и
  тестирует исполняемый файл для macOS (Apple Silicon) на macOS-раннере.
  Исполняемые файлы и архив прогона Linux-дымового теста с его рисунками
  выкладываются как артефакты. Пятое задание прогоняет тесты графического
  интерфейса и его самопроверку на Linux без экрана (`scripts/ci/gui.sh`)
  и выкладывает снимки экранов и архивы самопроверки (`gui-screenshots`).
* GitVerse CI (`.gitverse/workflows/build.yml`), при каждом пуше: та же
  Linux-сборка и тесты, и кросс-компилированный `AMORPH.exe` как артефакт
  (хранится 7 дней). У GitVerse нет Windows-раннеров, поэтому там
  исполняемый файл не запускается.

### Выпуски

`.github/workflows/release.yml` делает выпуски из раздела «Загрузка». Он
запускает задания `build.yml` (сборки, тесты и дымовые тесты трёх систем),
затем `scripts/ci/package_release.sh` упаковывает их артефакты вместе с
README и лицензиями и записывает контрольные суммы. Чтобы выпустить версию
1.2.0:

1. Укажите версию в `project(AMORPH VERSION 1.2.0 ...)` в `CMakeLists.txt`
   и в `AMORPH_VERSION` в `src/amorph_results.py` (тесты проверяют, что они
   совпадают; AMORPH печатает её в первой строке своего вывода, а архивы
   прогонов записывают её в `manifest.json`) и добавьте раздел `## 1.2.0`
   в `CHANGELOG.md`.
2. По желанию — пробный запуск: «Run workflow» для Release на вкладке
   GitHub Actions. Он собирает и упаковывает всё, с именами по версии из
   `CMakeLists.txt`, и выкладывает это как артефакт `release-v1.2.0`, не
   создавая выпуска; сводка запуска показывает примечания к выпуску.
   Pull request, изменяющий `CHANGELOG.md`, `release.yml` или его скрипты,
   получает такой же пробный запуск.
3. Поставьте тег на коммит и отправьте его на GitHub: `git tag v1.2.0` и
   `git push origin v1.2.0`. Процесс останавливается, если тег не равен
   `v` и версии из `CMakeLists.txt`. Он создаёт GitHub Release тега с
   файлами и примечаниями из раздела версии в `CHANGELOG.md`; у
   аннотированного тега, сообщение которого длиннее одной строки
   (`git tag -a v1.2.0`), примечаниями становится это сообщение.

`.gitverse/workflows/release.yml` зеркалирует выпуск на GitVerse при пуше того
же тега туда (`git push gitverse.ru v1.2.0`): ждёт GitHub Release, скачивает
семь его файлов, проверяет их SHA-256 и публикует их с теми же
примечаниями. В секретах репозитория GitVerse нужен `GITVERSE_API_KEY` с
правом «Репозитории → Запись». Выпуск v1.0.0 собирался на GitHub около
16 минут, а зеркало ждёт до 20 минут из своих 30
(`scripts/ci/download_release.sh`). Если GitHub Release собирается дольше,
зеркало завершается с ошибкой и сообщает об этом: когда в GitHub Release
появятся все семь файлов, выберите «Run workflow» для Release на GitVerse
и запустите его на теге, а не на ветке (действие создания релиза
принимает только ссылки `refs/tags/`).

Процесс запускается только на теге, в коммите которого он есть, поэтому
v1.0.0, поставленный до его появления, публикуется на GitVerse вручную,
один раз:

1. `bash scripts/ci/download_release.sh v1.0.0 ~/amorph-v1.0.0` скачивает
   семь файлов GitHub Release и проверяет их.
2. `bash scripts/ci/release_notes.sh v1.0.0` печатает его примечания.
3. На GitVerse создайте новый релиз существующего тега `v1.0.0` с
   названием «AMORPH 1.0.0» и этими примечаниями и приложите семь файлов.

`.github/workflows/validate.yml` сравнивает результаты двух версий
AMORPH: он запускает обе на четырёх входящих в комплект наборах данных и
выводит таблицу сводок апостериорного распределения (доля аморфной фазы,
форма широкой компоненты, параметры шума, числа пиков) и скорости каждого
запуска (сохранений в минуту). Это занимает
часы, поэтому запускается только по требованию: «Run workflow» на вкладке
GitHub Actions (эталонная версия — входной параметр, по умолчанию
master), или лейбл `validate` на pull request'е (эталон — база pull
request'а; повторное добавление лейбла перезапускает сравнение). Каждый
запуск сэмплера останавливается после 5000 сохранений или 210 минут,
в зависимости от того, что наступит раньше (оба значения — входные
параметры «Run workflow»), и то, что успело сохраниться,
постобрабатывается; лог каждого запуска сообщает число сохранений и
уровней каждые 10 минут.

`.github/workflows/experiment.yml` запускает наборы данных из
репозитория с настройками из `scripts/ci/experiment_settings.json`
(максимальные числа пиков, `narrow_peak_nu`, `control_points` и, по
желанию, другие настройки `config.yaml`), каждый с несколькими сидами, все
параллельно, и выводит таблицу доли аморфной фазы и того, сколько
апостериорного веса имеет доля 0 или ниже 0.2. С `"fraction_range"` она
также даёт долю в этом диапазоне, чтобы сравнивать прогоны на разных
участках одного скана. Запускается так же: «Run workflow» или лейбл
`experiment` на pull request'е.

### Диагностика апостериорного распределения

`scripts/diagnose_posterior.py` сообщает, хорошо ли определена доля
аморфной фазы запуска. Запустите его на папке завершённого запуска,
после `showresults.py`:

```bash
python scripts/diagnose_posterior.py src --data src/easy_data.txt --json diagnosis.json --table particles.csv.gz
```

Он выводит апостериорный вес с долей 0, ниже 0.2 и ниже 0.45; для каждого
из этих диапазонов — взвешенные медианы логарифма правдоподобия, числа
узких пиков и их формы ν, и невязку; а также вес частиц с числом узких
пиков, близким к максимальному. Диапазон с реальным весом при низкой
доле, с сотнями узких пиков при малом ν и тем же правдоподобием, что у
основной моды, означает, что данные не определяют долю. `--table`
записывает по одной строке на сохранённую частицу (несколько сотен
килобайт вместо сотен мегабайт `sample.txt`). `--range LOW HIGH` также
даёт долю в этом диапазоне x.

Рисование графика подгонки с помощью TikZ
=========================================

Скрипт `showresults.py` создаёт `posterior_sample.txt`, который содержит
апостериорные выборки модели, аморфной (широкой) компоненты,
кристаллических (узких) пиков и фона. `src/export_pgf.py` превращает эти
выборки в таблицы, которые может читать PGFPlots, а `doc/figures/xrd_fit.tex`
рисует график из них:

```
python showresults.py                     # в src/, пишет posterior_sample.txt
python export_pgf.py --data easy_data.txt --out ../doc/figures/pgf
cd ../doc/figures && pdflatex xrd_fit.tex  # пишет xrd_fit.pdf
```

или, всё в одну команду,

```
bash scripts/make_xrd_figure.sh easy_data.txt
```

Таблицы, которые записываются в `doc/figures/pgf/`:

| файл | содержимое |
| --- | --- |
| `xrd_data.dat` | x и измеренная интенсивность |
| `xrd_mean.dat` | x и апостериорные средние модели, аморфной компоненты, кристаллических пиков и фона |
| `xrd_samples_model.dat` | x и несколько апостериорных кривых модели |
| `xrd_samples_amorph.dat` | то же для аморфной компоненты |
| `xrd_samples_xtal.dat` | то же для кристаллических пиков |
| `xrd_samples.tex` | команды `\addplot` для бледных кривых выборок |
| `xrd_meta.tex` | макросы LaTeX: пределы осей, заголовок, доля аморфной фазы |

Первая строка каждого `.dat`-файла содержит имена столбцов без символа
комментария, например `x model amorph xtal background`. Поэтому эти таблицы
можно импортировать не только в PGFPlots, но и в Origin или LabPlot, указав
первую строку как заголовок и пробел как разделитель.

Полезные опции `export_pgf.py`:

* `--title` задаёт заголовок рисунка (это разметка LaTeX, по умолчанию —
  химическая формула образца).
* `--samples N` — число бледных апостериорных кривых на компоненту
  (`0` выключает их).
* `--max-points N` ограничивает общее число точек в кривых выборок, чтобы
  рисунок помещался в память pdfTeX. Используйте `--max-points 0` вместе
  с `lualatex` для полного разрешения.

Чтобы использовать рисунок внутри `doc/ms.tex`, а не как отдельный PDF,
добавьте `\usepackage{pgfplots}` в преамбулу и

```
\def\xrddatadir{figures/pgf/}
\input{figures/xrd_fit_body.tex}
```

`scripts/make_demo_posterior.py` генерирует синтетический набор данных и
соответствующий `posterior_sample.txt`, что удобно для проверки всей
цепочки без предварительного запуска сэмплера.
